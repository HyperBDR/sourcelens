Terminal outcome

终态证据判定

终态不再只看“skill 是否曾经成功”，而是同时检查 required capability 下是否仍存在 scope=unresolved 的失败记录。

Decision matrix

错误类型与封锁策略

错误分类由 gateway_model 统一生成恢复元数据，CapabilityBoundaryMiddleware 再按调用属性和累计次数执行门禁。

错误类别 典型信号 预算 / 封锁 影响范围
request HTTP 4xx、Unknown JSON field、参数为空、schema / syntax 相同请求 2 次；source 修正累计 4 次 Request，必要时 Source
transient HTTP 5xx、timeout、rate limit 相同请求 2 次；非幂等写仅 1 次 Request
configuration 401 / 403、auth、credential、permission 首次失败即停止该来源 Source
policy policy / budget / loop / repeated / stalled 不可由模型继续修正 Source；特殊全局预算为 Tool
tool 未能进一步分类的结构化失败 相同请求 2 次；source 修正累计 4 次 Request，必要时 Source

三个作用域如何构造

  • Capability：skill、mcp、workspace、 artifact_delivery，用于验证业务证据是否满足路由要求。
  • Source：Skill 使用 skill:<slug>； MCP 使用 mcp:<tool_name>；其他工具使用 tool:<tool_name>。
  • Request：工具名 + 参数规范化 JSON 的 SHA-256； 参数键顺序不同仍视为同一请求。
  • Skill 的通用入口不会因单一 source 封锁而从模型工具列表移除； 具体调用在 invocation gate 中按参数识别 source。
Warning-only 的首次可修正失败不会直接降低终态；只有达到预算并被记录为 scope=unresolved 的 required 失败，才会在已有成功证据时 强制终态为 partial。

Production scenario

本次生产场景在新流程中的落点

1 · 首轮错误保持隔离

两个 GitHub 参数错误只令 github source correction=2；两个 Jira 参数错误只令 jira source correction=2。没有 source 达到 4， 也没有相同 Request 达到 2。

2 · 修正调用继续执行

run_skill_artifact 仍暴露给模型。GitHub、Jira 可用新参数 修正；GitLab 调用不会被其他 Skill 的失败预算影响。

3 · 终态不再跨来源洗白

GitLab 成功只恢复 skill:gitlab-cli。若 GitHub / Jira 已达到预算且仍 unresolved，Run 有成功证据时保存为 partial，而不是 completed。
